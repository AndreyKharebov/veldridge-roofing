## Storage and shared conventions

IndexedDB database `veldridge-workspace-v1`, version 1:

| Store | Key | Value |
|---|---|---|
| content | literal `workspace` | `{ services: [], categories: [], articles: [], projects: [], settings: {} }` |
| media | id | Public image records |
| inquiries | id | Private inquiries, attachment bytes and notes |

IDs are stable **strings**, not indices. New records use a prefix and UUID (timestamp/random fallback); old seed IDs can be slugs. Frontend routes, anchors and references depend on these IDs. A MongoDB `_id` needs an explicit serialization/compatibility decision, not a silent replacement.

`saveRecord` adds `id`, `revision` (starts at 1) and ISO `updatedAt`. Updating an existing record requires its current revision and increments it. Stale or missing records are rejected. Imported/reset revisions can be timestamp-sized numbers. Original seeds may lack `updatedAt`. There is **no universal createdAt on content records** today.

Content text is trimmed and truncated to the maxima below, not always rejected for overlength. Optional text becomes `''`; optional image/category references generally become null. Normalizers whitelist persisted fields. Text arrays drop blank items and truncate excess items. Editors/readers use plain text, not arbitrary HTML.

## Service — content.services

The service itself is the category: Roof Replacement, Damage Repairs, etc. There is no second collection of service groups. Residential and Commercial are independent flags.

| Field | Type and actual rules |
|---|---|
| id | Stable string, generated by adapter |
| title | Required string, max 100; case-insensitive unique among all services, including archived |
| summary | Required string, max 500; Home card description |
| description | Optional string, max 4000; detail/care text |
| imageId | Required existing public-media ID |
| homeImageId | Optional existing public-media ID; defaults to imageId; old records can use a separate Home image |
| imageAlt | Required string, max 250 |
| iconKey | Optional bundled icon path, max 500 or null; legacy presentation metadata |
| propertyTypes | Nonempty deduplicated array containing Residential and/or Commercial; other values removed |
| order | Integer 1–9999, default 1; not necessarily unique; sort key, not display number |
| showOnHome | Boolean |
| status | active or archived; defaults to active |
| group | main or supporting; defaults to main |
| points | Up to 20 nonempty strings, max 300 each |
| eyebrow | Optional string, max 100 |
| cta | String max 80; fallback Discuss Your Project |
| tone | warm, white or muted; defaults to white |
| revision / updatedAt | Common adapter metadata |

Read-only derivations: `image`, `homeImage`, `icon`, `number`. Hydration sorts services by order then title. ServicesPage filters active records, groups main before supporting, then numbers the visible sequence continuously `01, 02, ...` across navigation/details/care cards. Never renumber stored order on archive. Home selects active showOnHome records. Contact selects active services plus `not-sure`.

Archival hides the service from Services/Home/new inquiry choices but preserves linked projects and historical inquiry labels. There is no permanent service deletion method. Published linked projects are not automatically archived.

## News category — content.categories

| Field | Type/rule |
|---|---|
| id | Stable string |
| name | Required string, max 80; case-insensitive unique |
| description | Optional string, max 500 |
| revision / updatedAt | Common metadata |

Deletion requires matching revision and no linked article of any status. Reassign articles first. Categories organize the admin; no public Blog categories/search/filter UI was requested.

## Article — content.articles

| Field | Type/rule |
|---|---|
| id | Stable string |
| title | Required in every status, max 150; not unique |
| summary | String max 600; card excerpt and reader introduction |
| imageId | Existing public-media ID or null |
| imageAlt | String max 250 |
| publishedAt | Actual calendar date YYYY-MM-DD, or empty; not ISO timestamp |
| categoryId | Optional existing news-category ID or null |
| status | draft, published, archived; default draft |
| sections | Ordered array, maximum 30 |
| sections[].id | String max 200; fallback section-N |
| sections[].heading | String max 200 |
| sections[].body | Plain-text string max 12000; reader preserves line breaks |
| source.label | String max 150 |
| source.url | String max 2000; optional HTTP/HTTPS URL without embedded credentials |
| revision / updatedAt | Common metadata |

Publishing additionally requires summary, cover, alt, publication date, at least one section and every section's heading/body. A draft can be title-only. Supplied references/date/source must still be valid in drafts. Source label and URL must be both present or both empty.

Reader structure: date → title → introduction → cover → heading/body sections → optional source → fixed Contact CTA. `image` is a derived URL. Blog displays published records, newest publishedAt first, with ID tie-break. Home displays the first three published articles. Future dates do not schedule anything: published status makes content visible immediately. No WYSIWYG or scheduling service exists.

## Project — content.projects

| Field | Type/rule |
|---|---|
| id | Stable string |
| title | Required string, max 150 |
| dialogTitle | Normalizer copies title; old seeds may have custom formatting |
| summary | String max 800 |
| serviceId | Required existing service ID, including for drafts |
| propertyType | Must be in the selected service's propertyTypes |
| property | Optional property description, max 150 |
| duration | Optional human-readable string, max 150; not numeric duration |
| material / finish | Optional strings, max 150 each |
| status | draft, published, archived; default draft |
| order | Integer 1–9999, default 1; not unique |
| photos | Ordered array, maximum 20 |
| photos[].id | Required string max 200; unique within project |
| photos[].mediaId | Required existing public-media ID, max 200 |
| photos[].alt | String max 250; required for every published photo |
| photos[].caption | Optional string max 250 |
| photos[].crop | Optional legacy object: finite scale in [1,4], finite left/top; invalid crop omitted |
| coverPhotoId | String max 200; references a photo ID, NOT a media ID; required to match when photos exist |
| work | Up to 20 nonempty strings, max 300 each |
| isDemo | Boolean illustrative-project flag; current new form defaults to true |
| revision / updatedAt | Common metadata |

Publishing also requires summary, at least one photo and alt on every photo. Drafts still need title, service, supported property type, valid photo references and a valid cover when photos are present. An empty installation must create an active service before a new project. Existing archived-service references remain valid for history; UI normally offers active services plus the currently selected service.

Derived read fields: photos[].src, coverPhoto, image, imageAlt, category (= serviceId), categoryLabel (= service title). Missing-cover fallback is for reading legacy records, not permission to save an invalid cover. Gallery uses published records ordered by order; initial 12 then batches of 6. Home uses the first four. Archival retains photos. Removing a project photo does not delete its shared media record.

## Public media — media store

| Field | Actual representation |
|---|---|
| id | String reference used by other entities |
| name | Upload filename or image fallback; import truncates to 200 |
| alt | Library metadata; new upload empty; contextual alt lives on service/article/photo |
| createdAt | ISO timestamp; used by current object-URL cache |
| assetKey | Optional stable source path for bundled legacy assets; never a build-hashed URL |
| imageBytes / imageType | Uploaded ArrayBuffer and MIME type stored in IndexedDB for WebKit compatibility |
| blob | Reconstructed on read; old data may contain a Blob; not a REST field |
| src | Hydrated transient object URL or bundled URL, never durable identity |

Uploads: 1–20 images per batch; nonempty JPEG/PNG/WebP; <=10 MiB each; MIME/signature agreement; decodable image; <=60,000,000 pixels. Validate the entire batch before atomic persistence. Project count limits are separate. No media-delete API or thumbnail generation exists yet.

After cleanup selectable media starts empty. Asset registry and files remain for static sections, old browser records and compatible backups; they do not automatically become selectable records. Server media should use metadata and storage keys/URLs, not Blob URLs or Vite hashes. Storage provider and processing/deletion policy remain future decisions.

## Inquiry — inquiries store

| Field | Type/rule |
|---|---|
| id | Generated string; UI removes INQ- prefix for display |
| name | Required trimmed string, max 100 |
| phone | Optional, but phone or email required; allowed punctuation and 10–15 digits; UI max 32 characters |
| email | Optional, syntax checked when present, max 254 |
| zip | Optional ZIP or ZIP+4 |
| service | Active service ID or literal not-sure |
| serviceLabel | Snapshot of service title at submission, or Not sure yet |
| message | Optional string max 4000 |
| source | null or {type: project|article, id, title}; frontend context limits ID to 120 and title to 240 |
| photos | Up to five PRIVATE attachments; same 10 MiB/type/decoding rules |
| photos[].id / name | Attachment ID and filename |
| photos[].imageBytes / imageType | Stored bytes/type, reconstructed as blob for admin viewer |
| status | new, in-progress, closed, spam; creation always new |
| notes | Ordered array, initially empty; append-only through current UI |
| notes[].id / body / createdAt | Generated ID, trimmed string max 4000, ISO timestamp |
| createdAt | Submission ISO timestamp; inbox newest first |
| revision | Starts 1; status/note update requires current revision |
| isDemo | Currently true for all local submissions |

Public submission receives values + File[] + source and returns only `{ id }`. Admin update receives `{status,note,revision}` and appends a nonblank note. Preserve source/service snapshots when content is archived or removed. Attachments never enter public media or content backups.

Backend gap: current direct createInquiry calls do not independently whitelist/validate source; frontend context normalization is not server security. Implement server whitelists, source validation, upload protection, rate limits and authorization. Do not expose the inbox/private attachments through public content reads.

| Field | Type/rule |
|---|---|
| company | Required string max 120; empty baseline retains known site identity Veldridge Roofing |
| phone | Required on ordinary save, max 40; at least 10 digits |
| email | Required on ordinary save, max 254; syntax check |
| street | Required on ordinary save, max 200 |
| city / state | Required on ordinary save, max 100 each |
| zip | Required on ordinary save, max 10; ZIP/ZIP+4 |
| hours / hoursNote | Optional strings max 200 each |
| timeZone | String max 80, Intl.DateTimeFormat validation; baseline America/New_York |
| serviceStates | Array filtered to PA/NJ/DE; baseline empty |
| map.latitude / longitude | Optional STRINGS max 30; numeric finite value within +/-90 / +/-180 |
| map.label | Optional string max 150 |
| socials.facebook/instagram/linkedin/youtube | Optional HTTP/HTTPS URLs without credentials, max 2000 |
| locality | Derived city/state/ZIP text, no empty separators |

The post-cleanup baseline is intentionally unconfigured. Ordinary Save settings remains strict. Only backup parsing permits the fully unconfigured baseline via `normalizeSettings(input,{allowUnconfigured:true})`; partially configured contacts still fail required-field checks. Company and valid timezone remain required. This exception is not a general bypass for saving invalid settings.

No office marker appears without an address. Even with address and coordinates, the current map is illustrative; no live map/geocoder exists. Do not label it accurate directions.

## Existing asynchronous adapter — no HTTP API yet

| Method | Input → result/effect |
|---|---|
| getContent() | Hydrated services/categories/articles/projects/settings/media; currently includes drafts for local UI |
| saveRecord(kind,input) | services/categories/articles/projects + record/revision → normalized record with ID/revision/updatedAt |
| deleteCategory(id,revision) | Deletes only unreferenced news category |
| saveSettings(input) | Complete settings with revision → saved settings |
| uploadMedia(files) | File[] → new media ID[] |
| getInquiries() | Admin inbox, newest first |
| createInquiry(values,photos,source) | Public fields/File[]/context → {id} |
| updateInquiry(id,{status,note,revision}) | Admin mutation → updated inquiry |
| reset() | Explicit UI confirmation → empty baseline; invalidates caches |
| exportBackup() | Admin → versioned JSON Blob |
| parseBackup(file) / importBackup(validated) | Validate then atomically replace content/public media; preserve inbox |
| auth.signIn / signOut / isSignedIn | Local sessionStorage demo only, not real authentication |

TanStack Query keys are `['workspace','content']` and `['workspace','inquiries']`. Mutations invalidate the relevant query or `['workspace']`. Same-origin tabs use BroadcastChannel. Preserve these return shapes or adapt HTTP responses within src/dev.

IMPORTANT: local getContent includes drafts/archives and relies on UI filtering. A production public endpoint must filter server-side and never return unpublished records, private notes or attachment access. Separate authenticated admin reads from public reads.

## Backup contract

`{format:'veldridge-content', version:1, exportedAt, content, media}`. Uploaded public bytes are embedded as dataUrl; bundled assets use assetKey. Import limits: 100 MiB file, 500 media records, 1000 per content collection; unique IDs and valid references. Validation order: categories → services → articles → projects → settings. Revisions renewed. Inquiries/private files are excluded. Import preserves inbox; reset clears it. Git branches do not preserve browser-only edits/messages.

## Static content outside this phase

Hero, About, testimonials, FAQ, introductory text, CTAs, navigation, layout, masks and motion settings stay static. No Hero/testimonial/FAQ endpoints should be inferred from this cleanup. User animation timing edits and pinned Media Picker actions remain intact.
